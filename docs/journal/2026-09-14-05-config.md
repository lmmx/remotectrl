**Scope boundary being drawn here, stated explicitly because it's not 100% spelled out in
one place:** `resolve()` only reads `.rc/remotes.toml` (if present) and `git remote -v`, and
returns a `{name: RemoteType}` mapping — it does not prompt interactively for the 2+
remotes/no-config case. The sources doc §3 describes an *interactive picker* for that case,
but frames it explicitly as `sumac sources`' own behavior ("this draft assumes `sumac sources`
is sumac's own command that calls into `remotectrl`'s Python API"), not something `remotectrl`
does itself — consistent with `remotectrl` having "no domain knowledge" (design doc §1) and,
by extension, no interactive UI. `resolve()` returning "everything `unsynced`" for that case
is the correct handoff point: it's up to the caller to notice and prompt.

**Open question surfaced, not resolved here — see OPEN QUESTIONS below:** what happens if
`.rc/remotes.toml` contains a value that isn't `unsynced`/`mirror`/`backup`? Neither design
doc addresses malformed config content.

**Outcome:** done, pending independent review (see below). `src/remotectrl/config.py`
(`RemoteType` enum, `resolve()`), `gitwrap.remote_names` added, `errors.ConfigError` added
(separate from `GitError` — a malformed config file is not a git subprocess failure, caught
before writing tests). 7/7 new tests pass, full suite 32/32.

**OPEN QUESTION (not resolved, conservative interpretation chosen to keep moving):** neither
design doc specifies what happens when `.rc/remotes.toml` names a type string outside
`unsynced`/`mirror`/`backup`. Chose: raise `ConfigError` immediately. Rationale for this being
the conservative choice: silently downgrading to `unsynced` would hide a typo'd config value
behind "sync just doesn't happen," which is a worse failure mode than a loud error for a
household tool where sync correctness is the entire point (design doc §7's own philosophy:
"a human should always see and clear this state deliberately" is stated for failed-push
markers, not malformed config, but the underlying preference for loud-over-silent in exactly
this class of situation transfers). **Needs your review before load-bearing** — this is
picked, not derived, and a different call (e.g. downgrade to `unsynced` with a warning) is
equally defensible from what's actually written down.

**Independent review** (subagent given only the src/ diff and the two cited design-doc
excerpts, no journal access, no test-suite access) found four things. Responses:

1. **Asymmetry flagged: unknown remote name → silent UNSYNCED, unknown config type-string →
   hard `ConfigError`.** Correctly identified as an asymmetry — this is exactly the open
   question already recorded above, and the asymmetry is the *point* of the conservative
   choice, not an oversight: an unknown remote name is expected, routine clone-to-clone
   variation (2026-09-13's resolved gap); an unknown type string is a config typo with no
   "expected" reading. Treating both the same (silent-unsynced) would hide the typo.
   Standing as recorded — still flagged for your review, not newly resolved by this response.
2. **`git remote` vs `git remote -v` in the sources-doc quote.** Confirmed non-issue — same
   name set, `-v` only adds URLs `remote_names` doesn't need. No change.
3. **Two of four "needs a test" items were already covered** (3-vs-2-remotes was not
   distinguished in code, but "config names an absent-locally remote → key missing, not
   UNSYNCED-valued" was already asserted via dict equality in
   `test_configured_name_absent_locally_is_dropped_not_surfaced`; the `ConfigError` path
   already had `test_unknown_type_string_raises_config_error`) — expected, since the
   reviewing agent was deliberately given no test-suite access.
4. **Real gap, fixed:** an empty-but-present `.rc/remotes.toml` takes the "config exists"
   branch and never applies the single-remote MIRROR default, which is easy to mistake for
   a bug (discontinuity between "no file" and "empty file"). Confirmed as *intentional*
   per sources doc §3 ("assigning roles is opt-in... a user can run `sumac sources` and
   decide not to configure sync at all") rather than fixed as a bug — an empty file is a
   deliberate "leave everything unsynced," not an incomplete no-config state. Added
   `test_empty_config_file_does_not_trigger_mirror_default` to lock this in, and tightened
   `resolve()`'s docstring to state the distinction explicitly instead of leaving it
   implicit. Also added `test_three_remotes_no_config_all_unsynced` for the count-boundary
   gap. Docstring's "left for the caller to prompt a human" phrasing (correctly flagged as
   overclaiming a signaling mechanism the code doesn't have) removed — reworded to state
   only what `resolve()` actually returns.
