# 2026-09-14: Unit — one-commit contract

**Attempting:** `src/remotectrl/onecommit.py::run_op(path, op) -> str`
**Derived from:** sumac design doc §6 ("The wrapped operation and its one-commit contract"):
`remotectrl.run(repo_path, op: Callable[[], None]) -> None`. "`op` must produce exactly one
commit... `remotectrl` snapshots `HEAD` before calling `op` and diffs against it after; if the
diff isn't exactly one new commit (zero, or more than one), that's a caller bug and
`remotectrl` raises loudly rather than attempt any push. No stronger check."
**Checkpoint before starting:** `/tmp/remotectrl-checkpoints/20260914T010625-before-onecommit`

Detecting "exactly one new commit" needs one more `gitwrap` primitive: a commit count between
two refs (`git rev-list --count <before>..<after>`), not just equality — zero commits and
two-or-more commits are both errors, and only a count distinguishes "one" from "more than
one" (HEAD-before != HEAD-after alone only rules out the zero case).

Naming this `run_op` rather than `run` (the design doc's literal name) because a bare `run`
in this module would collide in meaning with `preflight.run_preflight` and the eventual
top-level orchestration function once postflight exists — `run_op` names specifically what
this function does (runs the caller's op under the one-commit contract), leaving `run` free
for the composed preflight+op+postflight entrypoint the next units build toward. This is a
naming choice, not a behavior deviation from §6.

**Independent review** (diff-only) found:

1. **Deliberate addition, kept:** `run_op` returns the new commit hash (`str`), where §6's
   literal signature is `-> None`. Kept — a caller (postflight/markers, not yet written)
   needs the new commit hash for the pending-push marker's content, and returning it costs
   nothing the design doc forbids (§6 says nothing about the return value being meaningless,
   only that `op` itself shouldn't need to *return* the hash for the contract check to work,
   which this doesn't do — `head_commit` after `op()` is what's returned, not anything `op`
   provides).
2. **Not a gap I introduced, but worth locking in with a test:** the reviewer flagged that
   `rev-list before..after` assumes roughly-linear history, and a history-rewriting `op`
   (amend, hard-reset-and-commit) isn't specially detected. This is exactly what §6's "no
   stronger check... the snapshot/diff is sufficient" already accepts — the design doc
   deliberately rejects a stronger check (e.g. requiring `op` to return the expected parent)
   for simplicity, so an unusual `op` producing non-linear history is explicitly out of
   scope, not an oversight in this diff. Added
   `test_non_linear_history_is_not_specially_detected` (a `commit --amend` op) to document
   the actual behavior rather than leave it silently unverified — passes, and its own
   docstring says outright it isn't asserting correctness, just locking in current behavior.
3. Also caught myself, writing that test, about to reintroduce the exact `tests.conftest`
   cross-import bug fixed in the gitwrap-readonly unit (`from tests.conftest import _git`) —
   reverted before running, used the `git` fixture instead. Sibling-instance grep after the
   fact confirmed no other test file has reintroduced it either.
